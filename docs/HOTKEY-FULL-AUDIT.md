# Full native hotkey audit — alpha22 dev

Historical diagnostic record. Preserve the findings below; its alpha-specific setup is not the current exercise specification. See [Hotkey Trainer](HOTKEY-TRAINING.md) for current behavior and [development status](DEVELOPMENT-STATUS.md) before scheduling another audit.

Alpha24 separates menu cancellation and selection: context preparation leaves the new source unselected, the first tick cancels the old UI and clears selection, and selection happens after a 0.5-second wait. Dispatch waits a further second. Build/skill entry keys require a recorded submenu opening; if that does not arrive, the trial records `submenu-not-open` without sending another prefix or an entry key. This addresses the observed Altar placement preview during a Burrow trial without assuming the script sent Q twice: the alpha23 report dispatched Q, then W, and never recorded Build opening. Native verification is still required. Allow 2-3 hours with the additional settling time.

Alpha23 update: Cancel/Escape has been removed, leaving 652 entries and 2,058 planned trials. The fixture covers 640 exact bindings; the remaining 12 are unverified. Native command-button/tooltip alpha is now entirely unmanaged by the normal trainer/full audit. Alpha22 restored captured alpha every tick, which could retain a zero value captured before selection and overwrite engine refreshes; the user's double-click workaround prompted removal of that handling. A regression verifies that opacity changed by Warcraft is not overwritten. The archived alpha21 Stop isolation passed every tested opacity and remains evidence only for that case.

The alpha23 validation pass also removes all sight-radius overrides and custom prompt-icon clicks/tooltips. Prompt icons are inert backdrops; native tooltips remain intact. The full audit bypasses scoring, wrong-answer recovery and selection resets, and correlates registered command confirmations directly with the audit's key observations alongside independent native events. Its manual comparison buttons are suppressed. Use `-hotkey-full-audit-end` to save and stop, or the standard Menu to pause. The temporary Windows keep-awake helper prevents display/system idle, waits up to 15 minutes for a new audit, releases on completion/stop, and has a four-hour safety limit. No Windows power-plan settings are modified.

Start Hotkey Trainer, choose any race, then enter `-hotkey-full-audit` and close chat. Leave the game running without pressing keys or clicking. The run includes every race, not just the selected one. All spawned source units, buildings, patrons and summons are visible, along with the real command grid and native tooltips. The previous black cover/fog masking has also been removed from normal Hotkey Training at the user's request.

The plan contains all 653 catalogue entries three times, shuffled independently each repetition, plus native Stop controls before/after each repetition and every 20 entries (2,061 planned trials). Actual keys come from an explicit development fixture prepared from the tester's CustomKeys.txt. Research hotkey arrays use the requested research level. Exact supported letter bindings cover 640 entries; 13 entries have missing/unsupported bindings and are recorded as unverified, never guessed. No physical keystroke equivalence is claimed for ForceUIKey.

Allow roughly two hours. A failed initial Stop control is retried once, then stops the audit as inconclusive. Later controls are also retried; their health is recorded against subsequent outcomes, so loss of input can be separated from unavailable buttons. Menu pauses the activity. End saves and stops. Next/Retry remain diagnostic controls; do not use them during the automated run. Repeated runs overwrite the report filenames, so preserve a run before starting another.

Every context uses the real trainer setup and its current recognition; an independent persistent observer logs native events without relying on trainer filtering. Each trial also records selected source, prerequisite unit counts, required research counts, resources, technology limits, hero level/skill points, source ability levels and shop patron-order acceptance. Setup errors are captured so a problematic entry does not discard the rest of the run.

Outcomes remain separate: native-and-trainer, native-recognition-missed, activation-only, requirements-missing, no-key-notification, no-activation-evidence, unsupported-binding and setup-error. Targeted abilities/construction may activate targeting mode without emitting a spell/construction event; activation-only is not a failed execution or a proven false positive. Missing events alone are not proof of incorrect bindings. Three trials help identify consistency but cannot prove the absence of intermittent failures or validate untested keyboard modes.

Reports are saved automatically in bounded batches to `CustomMapData/JTG-Hotkey-Full-Audit-001.pld`, `002`, etc. `JTG-Hotkey-Full-Audit.pld` is the manifest containing current state, progress and batch count. Only batches named by the current manifest belong to the run. `tools/read-hotkey-full-audit.py MANIFEST` groups outcomes by prompt, flags inconsistencies/missing repetitions, and retains control health and setup errors. Native reports must be reviewed before declaring recognition reliable.

Run `tools/prepare-hotkey-comparison.py CUSTOMKEYS_PATH` before the development build. The binding fixture is excluded from release builds and contains no personal file paths. Regression mocks check registered entry points, full three-repeat coverage, independent native-vs-trainer classification, continuation after an unconfirmed entry, controls, visibility and cleanup; they cannot establish actual engine dispatch.
